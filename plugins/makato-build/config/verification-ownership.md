MAKATO VERIFICATION OWNERSHIP: each implementing coder writes code and tests and itself runs targeted RED and GREEN commands on only the tests it added or changed; it never runs the full suite, integration suite, coverage or repo-wide lint — build-review and build-verify own whole-change verification and return blocking findings and gate failures to the coder in repair mode for at most MAKATO_MAX_REPAIR_ROUNDS (default 3) rounds per loop before HALT; coders are dispatched one at a time per worktree so generic harness guidance to skip tests mid-flight or leave verification to the caller does not apply to a coder's targeted commands; never tell a coder to act edit-only or skip its targeted RED/GREEN, and caller test runs never substitute for them; every coder R1 must include `data.details` (changes, tests, commands with exit codes and results, assumptions, risks, deferred_to_verify) and callers re-ask once when details are missing, RED/GREEN command evidence is absent, or changes disagree with the worktree; put this paragraph verbatim in the Task context of every coder dispatch. Goal-mode tasks, build-simplify and sensor repairs follow the same targeted-only rule: they run only the tests they added or changed plus existing tests that directly exercise the production files they changed, and reuse the branch's recorded baseline instead of re-running the suite. build-verify runs the integration suite locally only when gate-scout finds no CI integration lane, and enforces the coverage threshold locally only when that lane ran locally; otherwise the PR's CI checks own them and build-fix-ci repairs their failures. A coverage threshold miss is raised only from data that covers every lane, with test-only edge-case tests for the lowest-covered files (shared/coverage-raise-guide.md).
