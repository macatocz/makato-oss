Goal Alignment

Does this skill serve the plugin's goal?

Plugin Goal — makato-build Transforms decomposed, vertically-sliced stories into tested, reviewed, merged code.

How This Skill Serves the Goal

push-to-git moves verified code from local working tree to the remote — the final local step before human review. It produces an atomic, bisectable commit history from the plan's task structure and pushes to the feature branch.

Without clean commits, a correct implementation is hard to review and impossible to bisect. The commit structure is not an afterthought — it directly determines how reviewable and maintainable the change is.

Position in Plugin Workflow

Phase 7a of 8 — after all gates pass in /verify, before /create-pr. The skill creates commits and pushes the branch. /create-pr then opens the pull request against that branch.

Commit model: one per task

Each task from the plan becomes one commit. This maps logical units of work to git history, keeping each commit individually bisectable. A commit that breaks bisect is a commit that doesn't belong.

Push confirmation

Commit creation is autonomous. The push to remote is confirmed with the user first — pushing affects shared state, triggers CI, and is visible to the team.

Workflow

Execution Steps

Step 1
Ask for work item key and load context
Ask: "Which work item are we pushing? (e.g. DCP-1234)" — or use the passed argument.

Read spec/<key>/plan.md. Extract the task list — task titles and their file targets. This defines the commit grouping.

Run git status and git branch --show-current. Verify we are NOT on main or master. If on a protected branch, stop and tell the user: "Cannot commit directly to <branch>. Create a feature branch first."
Step 2 logs
Log session start
Append to spec/<key>/build.jsonl:
{"ts":"…","skill":"push-to-git","story":"<key>","step":"session","status":"start","data":{"branch":"<name>","tasks":<N>}}
Step 3 gate
Verify clean starting state
Run git diff --stat HEAD to confirm there are uncommitted changes to commit. If the working tree is clean (nothing to commit), tell the user and stop — there is nothing to push.

Check for any untracked files that should be committed (new source files, new test files). Any untracked file in a source or test directory is a candidate — do not silently skip it.
Step 4 autonomous
Plan commit grouping from task structure
Load @references/commit-guide.md. Map each plan task to its changed files using the task's file targets from plan.md and the actual diff (git diff --name-only HEAD).

Group: all files that implement one task go in one commit. Tests for a task go in the same commit as the production code for that task — they document the behavior of that code and belong together.

Files that span multiple tasks (e.g. a shared utility modified by two tasks) go in the commit for the task that primarily introduced the change.

Any changed file not attributable to a specific task is grouped into a final catch-all commit: chore(<scope>): miscellaneous changes from <key>.

Present the planned grouping to the user:
Commit 1: feat(invoice): add status field to Invoice entity
        src/Invoice.java, src/InvoiceTest.java
Commit 2: feat(invoice): add InvoiceStatusService with transition logic
        src/InvoiceStatusService.java, src/InvoiceStatusServiceTest.java

Wait for the user to confirm or adjust the grouping before proceeding.
Step 5 autonomous
Create commits
For each planned commit in task order:
  • Stage exactly the files in that commit's group (git add <files> — never git add -A or git add .)
  • Create the commit with the conventional message from the plan
  • Verify the commit landed: git log -1 --oneline
Do not amend existing commits. If a commit fails, report the error and stop — do not proceed to the next commit until the failure is resolved.

Log each commit: {"step":"commit","status":"ok","data":{"sha":"<short>","message":"<msg>","files":<N>}}
Step 6 interactive
Confirm push to remote
Show the user the commits that will be pushed:
git log main..HEAD --oneline

Ask: "Ready to push <N> commits to origin/<branch>? This will trigger CI and be visible to the team."

Wait for explicit confirmation before pushing. If the user declines, the commits are local and safe — they can push manually when ready.
Step 7 gate
Push to remote
Run git push -u origin HEAD.

On success: record the remote branch URL from the push output.

On failure (rejected, no upstream, auth error): report the exact git error verbatim. Do not retry automatically — a push rejection may indicate the remote has diverged and requires a human decision.

Log: {"step":"push","status":"ok"|"error","data":{"remote_branch":"<name>"}}
Step 8 logs
Log session end and hand off
Append to spec/<key>/build.jsonl:
{"ts":"…","skill":"push-to-git","story":"<key>","step":"session","status":"ok","data":{"commits":<N>,"branch":"<name>"}}

Tell the user: "<N> commits pushed to <branch>. Next: run /create-pr."
