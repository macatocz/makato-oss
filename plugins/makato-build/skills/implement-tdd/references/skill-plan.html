Goal Alignment

Does this skill serve the plugin's goal?

Plugin Goal — makato-build Transforms decomposed, vertically-sliced stories into tested, reviewed, merged code.

How This Skill Serves the Goal

implement-tdd is where pland plans become actual code. It executes the task list from plan.md using a disciplined RED → GREEN → INTEGRATE → VERIFY loop per task. Every task it completes produces working, tested code — unit tests covering isolated behavior and integration tests covering real dependency boundaries.

Without this skill, a refined plan never becomes an implementation. It is the primary production engine of the entire build pipeline.

Position in Plugin Workflow

Phase 3 of 8 — runs after /refine (Phase 1) and optionally /grill-with-docs (Phase 2). Feeds into /simplify (Phase 4). For mixed-mode plans (tdd + goal tasks), only processes tasks marked mode: tdd; goal-mode tasks are handled by /implement-goal.

Workflow

Execution Steps

Steps 1–4 are setup. Step 5 is the per-task TDD loop (repeated for every tdd-mode task). Steps 6–7 close the session.

Step 1
Ask for work item key and load plan
Ask: "Which work item are you implementing? (e.g. DCP-1234)" — or use the passed argument directly.

Read spec/<key>/plan.md. If the plan does not exist: stop and tell the user to run /refine first.

Load @references/tdd-cycle-rules.md.

Extract all tasks where mode: tdd. If no tdd-mode tasks exist: tell the user all tasks are goal-mode and to run /implement-goal instead. If the plan is mixed, note which tasks are goal-mode and confirm they will be skipped: "Tasks [N, M] are goal-mode and will not be processed here — run /implement-goal for those after this session."
Step 2 logs
Log session start
Append to spec/<key>/build.jsonl:
{"ts":"…","skill":"implement-tdd","story":"<key>","step":"session","status":"start","data":{"tdd_tasks":<N>}}
Step 3 gate
Establish test baseline
Run the full existing test suite. Record the count of pre-existing failures. This is the baseline — the implementation contract is: no new failures introduced. Pre-existing failures are not the responsibility of this session.

Log: {"step":"baseline","status":"ok","data":{"pre_existing_failures":<N>}}

If the entire suite is red (many failures, broken environment): stop and report. Do not proceed with an unrunnable test suite.
Step 4
Read implementation context
Read spec/<key>/plan.md in full to understand: the full task list and ordering, patterns noted during /refine (from the plan's implementation notes), and existing dependencies flagged for reuse.

If spec/<key>/context-snapshot.md exists (produced by /grill-with-docs): read it now. The canonical term glossary constrains naming — use codebase terminology, not spec terminology, where they differ.

Log: {"step":"load-context","status":"ok","data":{"grill_context":true|false}}
Step 5 — Per-task TDD loop autonomous
Execute RED → GREEN → INTEGRATE → VERIFY for each tdd task
Repeat for each tdd-mode task in plan order:
🔴 RED
Write failing unit tests (dependencies mocked) AND failing integration tests (real boundary). Run them — they must fail. If a test passes without implementation, it is trivial — rewrite it to be meaningful before proceeding.
🟢 GREEN
Write the minimum production code to make unit tests pass. Follow patterns from /refine. Reuse existing dependencies — do not introduce new ones unless the plan explicitly notes they are required. Run unit tests only.
🔶 INTEGRATE
Extend implementation until integration tests pass against real dependencies. Do not loosen integration test assertions to force a pass — fix the implementation. Run integration tests only.
🟣 VERIFY
Run the full suite: unit + integration + pre-existing. Zero new failures allowed. If new failures appear: fix them before moving to the next task. Structural failures (approach must change) → escalate to user.

Log per phase:
{"step":"red","task":<N>,"status":"ok","data":{"unit_tests":<N>,"integration_tests":<N>}}
{"step":"green","task":<N>,"status":"ok","data":{"unit_passing":<N>}}
{"step":"integrate","task":<N>,"status":"ok","data":{"integration_passing":<N>}}
{"step":"verify-task","task":<N>,"status":"ok","data":{"new_failures":0}}
Step 6 gate
Final suite verification and coverage check
After all tdd tasks are complete, run the full suite one final time.

If design.md specifies a coverage threshold: check conditional coverage (branch/condition coverage) against it — not line coverage. Conditional coverage verifies that every branch of every condition has been exercised, which is the meaningful signal for logic-heavy TDD work. Line coverage alone can be met without testing all branches.

If conditional coverage is below threshold: identify uncovered branches and add targeted tests for those paths. Do not move on until coverage is met or the gap is explicitly acknowledged and logged.

Log: {"step":"final-verify","status":"ok","data":{"tdd_tasks_complete":<N>,"conditional_coverage":"<X>%","threshold_met":true}}
Step 7 logs
Log session end and hand off
Append to spec/<key>/build.jsonl:
{"ts":"…","skill":"implement-tdd","story":"<key>","step":"session","status":"ok","data":{"tdd_tasks":<N>,"goal_tasks_pending":<N>}}

Tell the user: "<N> TDD tasks implemented. Full suite passing. Next: run /simplify to check for complexity, or /implement-goal if goal-mode tasks remain."
