Goal Alignment

Does this skill serve the plugin's goal?

Plugin Goal — makato-contribute Help contributors participate in makato-suite development while keeping all content within the framework's guardrails.

How This Skill Serves the Goal

Contribution doesn't end when the PR opens. Bots leave drive-by comments mixed with real findings; closing them out cleanly is part of "participating in makato-suite development." This skill encodes the audit loop demonstrated on PR #36 — fetch, validate, rate, fix, reply — so contributors land their PRs with verified resolutions instead of ignoring bot noise or applying every suggestion blindly.

Position in Plugin Workflow

Sibling to makato-plugin-creator and makato-skill-creator. Those create content; manage-pr closes the loop after a PR is opened. Together they cover the full contributor lifecycle.

Decision Test

Q: "Does this skill demonstrably serve the goal of helping contributors land correct, goal-aligned content?" A: Yes — it directly addresses the bot-review burden every contributor hits after opening a PR in this repo.

Workflow

Execution Steps

  1. Resolve PR context. If user gives a PR number/URL, parse it. Otherwise infer from current branch via gh pr view --json url,number,headRepository,baseRepository,headRefName. Surface the resolved PR back to the user.
  2. Detect host. Inspect remote URL — if host is not github.com (e.g., github.tools.sap), every gh api call must include --hostname <host>. Loads @references/gh-cli-github-tools-sap.md.
  3. Fetch summary review. gh pr view <n> --json comments,reviews — captures top-level review summaries.
  4. Fetch line-level review threads. gh api --hostname <host> "repos/<owner>/<repo>/pulls/<n>/comments?per_page=100". Do NOT use --paginate — concatenated JSON arrays break json.load. If >100 comments, page manually with ?page=N.
  5. Check out the PR branch locally. gh pr checkout <n> so the file paths and line numbers in comments match what's on disk.
  6. Validate each comment. For each thread: read the referenced file at the cited line, grep for the symbol/pattern the bot mentions, and judge whether the claim matches reality. Loads @references/comment-validation-rubric.md.
  7. Rate each comment. Assign Validity (✅ Valid / ⚠️ Partially valid / ❌ Invalid), Severity (High / Medium / Low / N/A), and Quality (🌟 Awesome / ✅ Helpful / 🤷 Neutral / ❌ Misleading). Loads @references/severity-rating-rubric.md.
  8. Render the report. Print a Markdown table to the conversation using @templates/pr-comment-report.md — one row per comment with file:line, issue, validity, severity, quality, recommended action.
  9. Wait for approval. Ask the user which fixes to apply (e.g., "all valid", "1,3,4", "skip"). Do NOT modify files until the user explicitly approves.
  10. Apply approved fixes. Edit the cited file/line. Stage and commit with a conventional commit message: fix(<scope>): address PR bot review — listing each addressed comment ID in the body.
  11. Reply to threads on GitHub. For each addressed thread, post a reply via gh api --hostname <host> --method POST repos/<owner>/<repo>/pulls/<n>/comments/<comment_id>/replies -f body="...". Use canned phrasing from @references/reply-templates.md (Fixed / Won't fix / Already correct).
  12. Push and remind. Run git push on the PR branch. Remind the user to check CI status with gh pr checks <n> and to re-trigger the bot review if needed.
  13. Final summary. Report counts: comments fetched, valid, applied, replied. Note any threads left open (skipped or invalid) so the user can decide whether to dismiss them.
