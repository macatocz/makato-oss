Goal Alignment

Does this skill serve the plugin's goal?

Plugin Goal Transforms raw Jira features into PI-sized epics with vertically-sliced stories through structured discovery, interviews, and architectural analysis.

How This Skill Serves the Goal

The prototype skill answers "how does it feel to use this?" before decomposing into stories. By generating interactive, high-fidelity HTML prototypes of new UI surfaces, it validates UX decisions and catches usability issues that PRDs and architecture docs cannot surface. This reduces rework during implementation by making the user experience tangible before any code is written.

It bridges the gap between abstract requirements (PRD) and concrete implementation (stories) — stakeholders can click through the feature before committing to building it.

Position in Plugin Workflow

Phase 4 (optional) — after create-architecture, before decompose. Only invoked for features with UI surfaces. The prototype informs story slicing by making interaction boundaries visible.

Flow: create-prd → create-architecture → create-prototype → decompose

Key Characteristics

  • Output: Single self-contained HTML file (specs/{folder}/prototype.html)
  • Fidelity: High — uses real design tokens from the target app's design system
  • Interactivity: Buttons/forms respond with mock data, state transitions visible
  • Review: Built into the prototype itself (slide-deck pattern with feedback panels per UI surface)
  • Scope: Only new/changed UI surfaces, not the full app
  • Agent: Uses a dedicated prototype-builder agent (creative HTML generation, not doc-writer)

Workflow

Execution Steps

Step 1: Resolve Spec Folder & Load Artifacts

  • 1.1: Resolve spec folder from argument (ITDB key) or auto-detect most recently modified specs/{ITDB-KEY}-*/
  • 1.2: Load required: prd.md (user journeys, story sketches, UI scope), design.md (component design, data model, API endpoints)
  • 1.3: Load mandatory-if-exists: decisions.md (cross-session continuity, prior UX decisions), repositories.yml (target repos for design system research) CHANGED
  • 1.4: Gate check: If PRD has UI scope = No or no user journeys exist, abort with suggestion to skip to decompose
  • 1.5: Detect update mode — if prototype.html already exists, ask: refine or start fresh

Step 2: Design System Research CHANGED

  • 2.1: Read repositories.yml to identify target repositories (mandatory from prior phases)
  • 2.2: Spawn context-scout per repository with design-system-focused search:
    • Design tokens (colors, spacing, typography, radii, shadows)
    • Component patterns (buttons, forms, modals, navigation, tables)
    • Layout conventions (grid, sidebar, responsive breakpoints)
    • External design system references (e.g., Glow, shared component libraries loaded as dependencies)
  • 2.3: Synthesize findings into a design context summary (tokens map + component inventory)
  • 2.4: External design system handling: Design systems (like Glow) often live outside the feature repos and are loaded as dependencies. The context-scout looks for package references, import patterns, and config files that point to the design system. If found, note the design system name and version for the user to confirm.
  • 2.5: Fallback: If design system context is insufficient (no tokens found, no component patterns, no external DS identified), ask the user:
    • Storybook URL or design system documentation path
    • Screenshots of existing app surfaces (for visual reference)
    • Description of visual language (colors, fonts, component style)
  • 2.6: Future enhancement: A curated design system reference file may be added later to references/ when we have more experience with what's needed across projects

Step 3: Identify UI Surfaces to Prototype

  • 3.1: Extract from PRD: user journeys (end-to-end flows with decision points), story sketches mentioning UI outcomes
  • 3.2: Extract from design.md: component design (new components), API endpoints that surface to the user
  • 3.3: Derive a list of discrete UI surfaces (screens, dialogs, panels, states) that are new or significantly changed
  • 3.4: For each surface, identify: what the user sees, what they can interact with, what state transitions occur
  • 3.5: Present the surface list to the user for confirmation before proceeding

Step 4: Adaptive UX Interview (if gaps exist)

  • 4.1: Scan the identified surfaces for ambiguity: missing interaction patterns, unclear navigation flows, unspecified states (loading, error, empty, success)
  • 4.2: If well-specified (user journeys cover all surfaces, states are clear): skip interview, proceed to Step 5
  • 4.3: If gaps exist: ask targeted UX questions (max 3-5):
    • Key interactions: "When the user clicks X, what happens? Inline feedback, modal, or navigation?"
    • Navigation flow: "How does the user move between these surfaces? Tab navigation, breadcrumb, wizard steps?"
    • Responsive behavior: "Mobile-first or desktop-first? Which surfaces are mobile-critical?"
    • States: "What does the empty state look like? How about loading? Error recovery?"
  • 4.4: Park unanswerable questions as open questions (Q# system, persisted to decisions.md)

Step 5: UX Decision Stress-Test (Grill) NEW

  • 5.1: Before committing UX decisions to a prototype, offer to stress-test them: 
    AskUserQuestion:
  question: "I recommend stress-testing your UX decisions before generating the prototype. Shall I grill you?"
  options:
    - "Yes — challenge my interaction decisions (Recommended)"
    - "Skip — I'm confident, proceed to prototype generation"
  • 5.2: If accepted, invoke /grill scoped to the current spec folder. The grill targets UX decisions focusing on:
    • Interaction patterns that might confuse users
    • Missing states (error, empty, loading) that would break the experience
    • Accessibility gaps in the proposed interactions
    • Inconsistencies with existing app patterns
    • Navigation dead-ends or circular flows
  • 5.3: After grill completes, findings feed into prototype generation (resolved decisions improve the prototype, open questions become [ASSUMED] placeholders)

Step 6: Prototype Generation CHANGED

  • 6.1: Dispatch the prototype-builder agent (dedicated creative agent, not doc-writer). The agent internally loads prototype-quality.md as its own quality guardrails — the main skill does NOT load this reference into its own context. CHANGED
  • 6.2: The agent generates a single self-contained HTML file using the slide-deck review pattern:
    • Each identified UI surface = one slide
    • Left/main panel: live interactive prototype of that surface (with mock data, clickable elements, state transitions)
    • Right panel: feedback textarea for that specific surface
    • Step tracker at top showing all surfaces
    • Copy Feedback button aggregates all comments
  • 6.3: Styling requirements:
    • Use the target app's design tokens (from Step 2) for the prototype content
    • Use makato review chrome (nav, step-track, feedback panels) for the wrapper
    • Prototype content must look native to the target app
    • All CSS/JS inline (single file, no external dependencies)
  • 6.4: Interactivity requirements:
    • Buttons show click feedback (ripple, state change)
    • Forms validate and show success/error states
    • Modals/dialogs open and close
    • Navigation between connected surfaces works within the prototype
    • Uses mock data that represents realistic content (not "Lorem ipsum")
  • 6.5: HTML validation: After generation, validate the output is well-formed HTML that renders without errors (check for unclosed tags, valid structure, no broken JS) NEW

Step 7: Open & Collect Feedback CHANGED

  • 7.1: Write to specs/{folder}/prototype.html
  • 7.2: Open in browser using platform-aware command:
    • macOS: open
    • Linux: xdg-open
    • Windows: start
  • 7.3: Tell user: "Prototype is open in your browser. Each slide shows one UI surface. Interact with the prototype, then add feedback in the right panel. Click 'Copy Feedback' when done."
  • 7.4: If revisions requested: parse feedback, re-dispatch prototype-builder agent with changes, re-open
  • 7.5: If approved: proceed to handoff

Step 8: Parked Questions Persistence

  • Write all unresolved UX questions to decisions.md Open Questions table
  • Priority: High = blocks decompose, Medium = resolve before implementation, Low = dev team decides

Step 9: Status & Handoff

  • Display completion summary: surfaces prototyped, design tokens used, feedback incorporated
  • Next step: /decompose (story slicing — prototype informs interaction boundaries for stories)
  • Note: Grill is invoked BEFORE generation (Step 5), not after. The prototype is the validated output — grilling it afterwards would be too late to influence its content cost-effectively. CHANGED

Design Decisions

  • No templates/ directory — prototype content is fully dynamic (varies per feature's UI surfaces)
  • Single HTML output — not prototype/index.html subfolder as originally noted in README. A single file is simpler to share, open, and review.
  • Review built into prototype — no separate review HTML. The prototype IS the review artifact.
  • Dedicated agent — prototype-builder handles creative generation; doc-writer stays focused on structured documents.
