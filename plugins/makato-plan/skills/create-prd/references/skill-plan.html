Goal Alignment

Does this skill serve the plugin's goal?

Plugin Goal (makato-plan) Transforms raw Jira features into PI-sized epics with vertically-sliced stories through structured discovery, interviews, and architectural analysis.

How This Skill Serves the Goal

create-prd takes grilled brainstorming output (brainstorm.md + decisions.md) and transforms it into a formal PRD. The PRD captures the WHAT and WHY: problem statement, success metrics, scope boundaries, and rough vertical story ideas that give direction for architecture and decomposition downstream.

Story fidelity: User stories in the PRD are rough ideas — directional sketches showing how work could be sliced vertically. They are NOT final artifacts. Detailed acceptance criteria and refined stories come later during spec/decomposition phases.

Position in Plugin Workflow

Step 2 in the shaping pipeline. Receives brainstorming artifacts (already imported ITDB, already resolved key decisions), produces structured requirements that feed architecture and decomposition.

Workflow

Execution Steps (Revised)

Step 1: Resolve Spec Folder & Load Artifacts

1.1 Resolve spec folder — From argument (ITDB key) or auto-detect most recently modified specs/{ITDB-KEY}/ folder. The folder already exists (created during brainstorming).

1.2 Load brainstorming artifacts — Read brainstorm.md (selected approach, rejected alternatives, edge cases) and decisions.md (resolved decisions + open questions). These are the primary input — no ITDB re-import needed.

Changed from v1: No ITDB fetch. Brainstorming already imported the ticket, attachments, and context. We trust those artifacts as our source of truth.

1.3 Open Questions startup check — If decisions.md has open questions (High/Medium priority), present them for resolution before proceeding. These may have been parked during brainstorming or a prior grill.

1.4 Detect update mode — If prd.md already exists in the folder, ask: "PRD already exists. Refine it or start fresh?" If refine, load existing PRD and show current content summary.

Step 2: Repository Identification & Research

2.1 Identify repositories — Check if specs/{folder}/repositories.yml exists (may have been set in a prior phase). If not, ask user which repos are affected. Store result for PRD frontmatter and codebase research.

2.2 Codebase research — Spawn context-scout agent to scan context/{repo}/ directories for existing implementations, patterns, and constraints. Return synthesized findings.

Step 3: Product Strategy Interview

Key change: This is NOT gap-filling. This is product strategy and goal-driven elicitation. Even with rich brainstorming artifacts, the PRD phase must sharpen: success metrics, priority, phased rollout approach, and non-goals. Don't assume the brainstorm covered everything — the brainstorm was about exploration, this is about commitment.

Interview areas (always covered, even if partially addressed in brainstorm):

  • Success criteria — 3-5 measurable KPIs (push back on vague: "What does 'fast' mean?")
  • Scope boundaries — explicit In-Scope and Non-Goals (what are we NOT building?)
  • User personas — who benefits and how (sharpen from brainstorm's broad categories)
  • Constraints & dependencies — timeline, tech stack mandates, compliance, budget
  • Priority — critical/high/medium/low with rationale
  • Phased rollout thinking — what's MVP vs. enrichment? (dependency-based, NOT time-based)

Park unanswerable questions (load @references/open-questions.md for parking protocol).

Step 4: Decision Stress-Test (Grill)

Invoke /grill scoped to the current spec folder, targeting business/UX decisions. This catches gaps BEFORE committing them to a PRD document. Grill findings update decisions.md directly.

Changed from v1: Grill is integrated INTO the PRD workflow (not optional). We grill before writing, not after. The user can skip if they explicitly confirm confidence.

Step 5: PRD Generation

5.1 Vertical story sketching — Based on interview + brainstorm + grill outcomes, sketch 3-5 rough vertical story ideas. Each story shows: user outcome, which layers it touches, and a brief acceptance sketch. Load @references/vertical-slicing.md for slicing rules.

5.2 Write PRD — Dispatch doc-writer agent with: brainstorm findings, interview results, grill decisions, codebase research, and PRD template. PRD references decisions by ID ("Per D3: ..."), never duplicates. Output: specs/{folder}/prd.md.

5.3 Delivery recommendations — Advisory section in the PRD: estimated scope (small/medium/large), suggested Epic count, story groupings, affected repositories. Purely advisory — no Jira creation.

On scale detection: We don't count stories or estimate tasks at this point (stories are rough ideas). Instead, scope estimation is qualitative: based on cross-repo breadth, dependency complexity, compliance requirements, and the grill's risk assessment.

Step 6: Parked Questions Persistence

Write ALL unresolved questions from this session to decisions.md Open Questions table. Zero silent loss guarantee. Priority: High = blocks next phase, Medium = should resolve in architecture, Low = can defer.

Step 7: HTML Review & Approval

Dispatch doc-writer agent with the makato design system template (templates/prd-review.html) to generate an interactive slide-deck review. Sections: PRD summary, story sketches, delivery recommendations, decisions referenced, open questions. User provides feedback via textareas, copies all, pastes back.

Iterate until approved.

Step 8: Status & Handoff

Mark PRD status (Draft → Approved). Show next steps based on qualitative scope assessment:

  • Small scope — skip design doc, proceed to spec
  • Standard scope — proceed to architecture design
  • Large/compliance scope — architecture + security review

Key Decisions

Adaptation Decisions (Final)

What We Keep

  • Vertical slicing as core story requirement with validation rules
  • PRD quality standards (no vague criteria, dependency-based phases)
  • decisions.md reference by ID ("Per D3: ...") — never duplicate content
  • Delivery recommendations (advisory Epic sizing, story grouping)
  • Parked questions persistence to decisions.md (zero-loss guarantee)
  • Open questions startup check (revisit prior session's parked Qs)
  • Repository identification for PRD frontmatter + codebase research
  • HTML review approval gate with makato design system
  • Handoff routing based on scope assessment

What We Change

  • No ITDB re-import — brainstorming did that; we trust brainstorm.md + decisions.md
  • Folder already exists — named specs/{ITDB-KEY}/ (created during brainstorming)
  • Stories are "rough ideas" — directional sketches, not detailed artifacts. Called "Story Sketches" in template
  • Grill is integrated — invoked BEFORE writing (not optional/after). User can skip with explicit confirmation.
  • Scale detection is qualitative — no story counting (they don't exist as countable things yet). Assessment based on cross-repo breadth, dependency complexity, compliance flags.
  • Interview is product strategy — not gap-filling. Always covers success metrics, scope boundaries, priority, phased rollout. Even rich brainstorms need these sharpened.
  • Update mode auto-detected — if prd.md exists, ask to refine or start fresh. No separate --update flag needed.

What We Drop

  • Jira Story creation (Phases 6.7, 6.8) — downstream skill responsibility
  • Confluence publishing (Phase 7) — downstream skill
  • Folder renaming with Feature key — folder is ITDB-named from start
  • Jira attachment import — already done in brainstorming
  • Cross-cutting preamble files — makato-plan uses local references
  • Persona section in SKILL.md — interaction style inlined into workflow
  • workflow-state.json — deferred discussion; for now, repos stored in PRD frontmatter
