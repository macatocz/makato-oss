Goal Alignment

Does this skill serve the plugin's goal?

Plugin Goal (makato-plan) Transforms raw Jira features into PI-sized epics with vertically-sliced stories through structured discovery, interviews, and architectural analysis.

How This Skill Serves the Goal

create-architecture fills the critical gap between "what we're building" (PRD) and "how to slice it into stories" (decompose). Without architectural clarity, story decomposition produces technically naive slices that collapse during implementation.

It answers the HOW question: system context, component design, data model, API contracts, security implementation, deployment strategy, and technical constraints.

What it does NOT produce: No task lists, no stories, no implementation plans. It produces a single architecture document (design.md) that provides technical context for downstream phases.

Position in Plugin Workflow

Phase 3 in the shaping pipeline:

brainstorming → create-prd → create-architecture → create-prototype (optional) → decompose → publish

The Boundary Rule PRD says the "what" (page loads in <2s). Architecture says the "how" (use CDN + edge caching). If a requirement specifies implementation, it's in the wrong document. If an architecture choice lacks a requirement justification, it's an unsupported decision.

Audience

Lead architects and team architects. The interview is designed for people who can make deep technical decisions about stack, integration, data flow, and constraints.

Persona

Technical, analytical, evaluates trade-offs. Documents decisions with rationale ("We chose X because Y"). Challenges vague answers the same way PRD rejects "fast" or "easy" — "microservices" without justification gets pushed back on, "we'll use a cache" needs cache type + invalidation strategy.

Output

A single file: design.md — the technical companion to the PRD. Plus updates to decisions.md (architecture decisions appended) and repositories.yml (confirmed/expanded).

Workflow

Execution Steps (9 Steps)

Same structure as create-prd: Interview → Grill → Generate → Validate → Review → Approve. The grill fills decisions.md gaps, then the document is generated from all collected input. The HTML review shows the generated document for approval (not raw interview answers).

Step 1: Load artifacts (PRD, decisions, repos, reference/) ↓ Step 2: Confirm/expand repositories + context-scout research ↓ Step 3: Architecture interview (3 rounds with architects) ↓ Step 4: Grill (optional) → findings → decisions.md ↓ Step 5: Generate design.md (doc-writer, using all collected input) ↓ Step 6: Completeness validation (flag AI assumptions) ↓ Step 7: Parked questions → decisions.md ↓ Step 8: HTML review & approval loop (browser gate) ↓ Step 9: Status & handoff (next: prototype or decompose)
1
Resolve Spec Folder & Load Artifacts

Same pattern as create-prd: resolve specs/{ITDB-KEY}-*/ from argument or auto-detect. Load:

  • prd.md (required) — the "what" that drives architectural decisions. If missing or Draft, warn and suggest completing PRD first.
  • decisions.md — cross-session continuity, existing decisions from brainstorming + PRD
  • repositories.yml — if already identified (from PRD phase)
  • reference/ folder — scan for technical documents (architecture diagrams, T-shirt sizings, API specs, DB schemas). Use markitdown MCP if unconverted originals exist.

Open Questions startup check + Update mode detection (same as PRD).

2
Repository Identification & Codebase Research

Always ask, even if repositories.yml exists from PRD phase. Architects often identify additional repos the PO didn't know about.

  • If repos exist: "PRD identified {repos}. From a technical perspective, are there additional repositories affected? Any to remove?"
  • If no repos: "Which repositories does this feature affect? Think about: data layer, API layer, UI, shared libraries, infrastructure."

Spawn context-scout per identified repo. Research focus:

  • Existing architecture patterns and conventions
  • Integration points, service boundaries, middleware
  • Data models, API contracts, auth patterns
  • Technology constraints (frameworks, platform mandates)
Updated: always confirm repos, even if existing
3
Architecture Interview (3 Rounds)

Comprehensive interview targeting lead/team architects. Every design.md section must trace to interview answers, PRD content, or context-scout findings.

Round 1 — System Context & Boundaries (always)

  • System context — "How does this feature interact with external systems? What's the boundary between what we own and what we consume/produce?"
  • Component breakdown — "Which components need to change or be created? How do they communicate (sync/async, protocols)?"
  • Data flow — "Trace the data from input to output. Where does it enter, get transformed, persist, and exit?"
  • Technical constraints — "What's non-negotiable technically? Language, framework, platform, deployment target, protocols, team capabilities?"
  • Integration points — "What services, APIs, or systems do we integrate with? Owned or external? Sync or async? What happens when they're down?"

Round 2 — Design Decisions & Data (always)

  • Key technical decisions — "What are the 3-5 most makatoful technical choices? For each: options considered, chosen approach, rationale, trade-offs accepted."
  • Data model — "What entities exist? Relationships? Storage technology? Schema evolution strategy? Data volume expectations?"
  • API design — "REST/GraphQL/gRPC? Key endpoints/operations? Versioning strategy? Authentication/authorization approach? Error handling patterns?"
  • Security considerations — "Authentication mechanism, authorization model (RBAC/ABAC), data sensitivity classification, encryption at rest/transit, compliance mappings from PRD NFRs."

Round 3 — Operations & Quality (always, depth varies by scope)

  • Performance approach — "How do we meet the NFRs from the PRD? Specific techniques: CDN, caching (type + invalidation), pagination, lazy loading, connection pooling. Where are the bottlenecks?"
  • Deployment strategy — "Blue-green, canary, feature flags? Rollback plan? Environment topology (dev/staging/prod)? Infrastructure as code?"
  • Observability — "What do we monitor? Key metrics, alerting thresholds, logging strategy, distributed tracing? How do we know it's healthy?"
  • Test strategy — "Unit/integration/e2e split? Coverage targets? Critical test scenarios? Performance/load testing approach? Contract testing for APIs?"
  • Migration & rollback — "Data migration needed? Backwards-compatible? Rollback steps if deployment fails? Feature flag kill switch?"

Parking protocol: same as PRD — "I don't know" or "need to check with X" gets a sequential Q# ID in decisions.md. Priority: High = blocks decompose, Medium = resolve before implementation, Low = dev team can figure out.

4
Decision Stress-Test (Grill)

Optional but recommended. Same pattern as PRD: ask user, invoke /grill scoped to spec folder.

Focus areas for architecture grill: missed integration points, scalability gaps, security blind spots, deployment risks, coupling concerns, single points of failure, missing fallback strategies, over-engineering vs. under-engineering.

Grill findings written back to decisions.md. These feed directly into design.md generation (Step 5).

5
Design Document Generation

Dispatch doc-writer agent to write specs/{folder}/design.md.

  • Load @references/architecture-quality.md for quality standards
  • Load templates/design-template.md for document structure
  • Input: PRD context, interview results (all 3 rounds), grill decisions, codebase research, technical reference documents
  • Decision references: use "Per D#: ..." pattern (same convention as PRD)
  • NFR mapping: each PRD NFR (the "what") maps to a concrete technical approach (the "how")
  • Append new architecture decisions to decisions.md (category: "Architecture")
  • Write/update repositories.yml with confirmed repo list
@references/architecture-quality.md templates/design-template.md
6
Completeness Validation

Same as PRD: verify every design.md section traces to user input (interview answers, confirmed context-scout findings, or grill outcomes). Flag AI-assumed content. Present for confirmation/correction/removal.

The interview must be comprehensive enough that every section can be filled. If multiple sections are AI-assumed, it means the interview missed those topics — go back and ask.

Emphasis: interview completeness prevents assumptions
7
Parked Questions Persistence

Write ALL unresolved questions to decisions.md Open Questions table. Zero silent loss.

Priority: High = blocks decompose phase, Medium = should resolve before implementation starts, Low = dev team can decide during refinement.

8
HTML Review & Approval

Dispatch doc-writer to generate interactive HTML review using templates/design-review.html.

Slides: System Context & Boundaries, Component Design & Data Flow, Technical Decisions (options/rationale), Data Model & API Design, Security & Performance, Deployment & Observability, Test Strategy, Open Questions.

Same change-highlighting pattern as PRD for update mode (green = new, amber = changed, red = removed).

Feedback loop: If revisions requested → parse feedback → adjust design.md → re-dispatch doc-writer → re-open review. Repeat until approved.

templates/design-review.html
9
Status & Handoff

Mark design.md status: Draft → Approved. Display next-step routing based on feature characteristics:

  • If UI feature (PRD "UI Required" = Yes/Minimal) → suggest /create-prototype
  • If no UI or prototype already done → suggest /decompose (planned)
  • Optional: /grill for additional stress-testing of the design doc independently
Key Decisions

Design Choices (v2 — feedback applied)

Repository Identification Resolved: Option C

Keep in PRD as optional ("Skip — determine in architecture phase"), make mandatory in create-architecture with expansion. Architects always confirm and may identify additional repos the PO didn't know about.

Document Generation Order

Same as PRD skill: Interview → Grill → Generate → Validate → HTML Review. The grill fills gaps in decisions.md. The doc-writer then generates design.md from ALL collected input (interview + grill + research). The HTML review shows the generated document — this is where human approval happens.

Rationale: You can't meaningfully review raw interview answers in isolation. The document synthesis is where gaps become visible. The completeness validation (Step 6) catches any AI assumptions before showing the review.

What we adopt from ai-first

  • Prerequisite check (PRD must exist, ideally Approved)
  • Repository identification + context-scout dispatch
  • decisions.md cross-session continuity
  • Technical interview structure (system context, data, API, security, deployment, testing)
  • Update mode with change tracking
  • Subagent delegation (doc-writer for generation)

What we do differently

AI-First (16 steps)

  • No grill integration
  • No HTML review gate
  • No completeness validation
  • Updates Jira directly (side-effect)
  • Separate references.md output file
  • Explorer subagent for live code
  • Attaches design doc to Jira

makato-plan (9 steps)

  • Grill integration (Step 4) — stress-test decisions
  • Interactive HTML review (Step 8) — browser approval
  • Completeness validation (Step 6) — no AI assumptions
  • Pure document output — no Jira side-effects
  • References in reference/ folder (from brainstorming)
  • context-scout for static context
  • Publish is a separate downstream skill

No stories, no tasks

This skill produces design.md only — an architecture document answering "how we build it". It does NOT produce stories, task lists, or implementation plans. That's the decompose skill's responsibility.

Interview comprehensiveness

The interview is designed for deep technical discussions with architects. All 3 rounds are mandatory (though Round 3 depth scales with scope). If the completeness validation flags gaps, the skill goes back to ask rather than assume.

architecture-quality.md content plan

  • Every technical decision: options considered, chosen approach, rationale, trade-offs accepted
  • NFR mapping: each PRD NFR must have a concrete implementation approach
  • Reject vague: "microservices" needs service boundaries; "cache" needs type + invalidation + TTL
  • System context described textually (C4-style), not drawn
  • Security section mandatory: authn + authz + data classification + compliance
  • Decision references by ID ("Per D#: ...") — same convention as PRD
  • Anti-patterns: no implementation without justification, no "we'll figure it out later" for critical paths

design-template.md sections

  • Frontmatter (Status, Feature, Created, Author, Repositories)
  • Overview (Summary, Goals from PRD, Non-Goals from PRD)
  • System Context (boundaries, external systems, data flow)
  • Component Design (breakdown, communication, responsibilities)
  • Technical Decisions (options/rationale table)
  • Data Model (entities, relationships, storage, evolution)
  • API Design (endpoints/operations, auth, errors, versioning)
  • Security (authn, authz, encryption, compliance mapping)
  • Performance & Caching (NFR implementation mapping)
  • Deployment & Operations (strategy, environments, rollback)
  • Observability (monitoring, alerting, logging, tracing)
  • Test Strategy (types, coverage, critical scenarios)
  • Migration & Rollback (data migration, backwards compat)
  • Key Decisions Referenced
  • Open Questions
